# 追加改修候補：複数依頼の追跡・無応答・復旧

記録日：2026-11-10。状態：**バックログ／設計提案、未実装・未検証**。

[dots接続設計](dots-integration.ja.md)の無応答対策を具体化する、Phase 4の接続候補向け追加項目。既存の実装順序・初期版の完了条件は変更しない。タスク台帳は変動する作業状態であり、長期記憶snapshotや既存のadoption run_idとは別の責務である。

## 背景：仕様・報告・推測を分ける

- **公式の想定用途**：dotsは複数の仕事を追跡し、バックグラウンドエージェントを並列実行しながら主会話を続けられる。複数依頼で返信不能になることを正常仕様とは確認できない。一方、無制限の並列実行を保証する記述でもない。
- **利用者報告（11/9）**：複数タスクの追跡漏れ・指示忘れ。
- **利用者報告（11/4）**：各タスクの更新が主会話に混在し、判断待ちの質問を見落としやすい。
- **無応答の別事例（10/17）**：既読・computer Readyでも全端末で無応答、通常ChatGPTは動作、429を観測という投稿。当時OpenAIサポートが問題把握・修正中と回答したが、現在の個別事象との同一性は不明。
- **委任タスクの別事例（10/4）**：27時間以上inProgressのまま、Stop失敗という公開Issue。

これらは同一障害の証明ではなく、「複数依頼が直接原因」「記憶整理でフリーズを修復できる」とも結論できない。OpenClawのキュー仕様・不具合をdotsの仕様として引用しない。実際の会話・アカウント情報・個別タスクIDは公開しない。

## 追加改修項目（案）

| ID | 改修候補 | 必要な性質 |
|---|---|---|
| DMR-01 | 依頼単位の永続台帳 | project/task/requestを識別し、受付・実行・成果確認・配送確認を分離。同じ依頼の照合キーを保持し、再送だけで新しい作業を起こさない |
| DMR-02 | タスク別文脈と優先順位 | 目的・完了条件・依存先・優先順位・想起バンドルをタスク単位で参照。別タスクの追加で既存依頼を黙って上書きしない |
| DMR-03 | 状態・待機理由の可視化 | queued/running/waiting_input/waiting_approval/waiting_dependency/paused/completed/failed/unknown等を提案語彙とし、最終観測時刻・根拠・次の手順を保持。見えない状態はunknownとする |
| DMR-04 | 無応答の分類と主会話の維持 | 受付未確認、処理待ち、委任停止、承認・接続待ち、配送失敗を区別。sleepや一つの委任待ちで他タスクの状態照会まで必須待ちにしない |
| DMR-05 | 中断・復旧と二重実行防止 | checkpoint・副作用・受領証を照合し、結果不明の書込み・送信を自動再試行しない。再開前に現在の許可を確認し、元の依頼との関連を維持 |
| DMR-06 | 同時実行・予算境界 | 対象が許す範囲でタスクを分離し、必要なら投入上限と待機順を設定。具体的件数は未決定。主dotと委任Work/Codexの利用枠を混同しない |

語彙・schema・状態遷移・adapterで取得できる観測は実装前に別途固定する。この表は既存APIの説明ではない。既存のoperation ID／run_idを持つだけで上記が実装されたとは扱わない。

## 受入候補（合成fixture、今回は実行しない）

1. 独立した依頼A/Bで、Bの追加後もAの目的・状態・完了条件を保持し、成果物と返答が元の依頼に対応づく。
2. Aが承認・接続・依存先待ちでも、理由を表示し、Bの状態照会を見失わない。未観測の実行継続を断言しない。
3. 受付未確認・既読だけ・進行中表示だけ・成果確認・配送確認を区別し、無応答を「忘れた」「完了」と分類しない。
4. timeout／ACK喪失後、保存済み結果と副作用を照合するまで再送しない。安全な再開でも同じ依頼との照合を維持し、二重適用しない。
5. 主タスクPause・委任Stop・スケジュール取消を区別し、一つの停止確認から他の停止完了を推定しない。

実装時は関連する少数ケースを選び、既存の試行単位のテスト予算を守る。この5項目は将来の受入案であり、現在の合格件数ではない。

## 運用・評価の境界

- 受付未確認数、追跡漏れ、未応答滞留時間、観測の鮮度、重複副作用、手動復旧回数、費用を記録候補とする。未知の状態は欠測として報告。
- 想起あり／なしの効果と、サービス障害・レート制限・接続・承認待ちを分ける。サービス停止の改善を記憶性能の改善として計上しない。
- この文書だけで新API権限・監視・自動督促・定期処理・外部送信を作らない。対象側の権限・承認・停止ルールを維持する。
- 外部ハーネスがdots内部のセッションやスケジューラを修復できるとは限らない。必要な場合は観測した時刻・版・エラー等を保存して公式サポートで切り分ける。dot削除・初期化は実行しない。
