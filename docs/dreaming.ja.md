# Sleep / dreaming の実行設計

状態：設計提案。ランタイム、定期実行、OpenClaw接続、モデル呼び出しは未実装・未実施。[全体設計](architecture.ja.md)の sleep 部分を具体化する。[OpenClawとの対応](research-basis.ja.md#openclaw-dreaming)と[ADR 0003](decisions/0003-grounded-dreaming.md)も参照。

## 1. 「寝る」「夢を見る」「覚える」を分ける

- **Sleep**：通常タスクの外で、固定した経験を整理する一回の処理。利用者への応答を止めることではない。
- **Light**：証拠の取り込み条件を確かめ、重複・訂正・候補を整理する。
- **REM**：複数の経験から共通点、矛盾、別の解き方、検証問題を提案する。推測を事実には変えない。
- **Deep**：根拠確認済みの候補から、採用を検討する記憶差分を構成する。性能評価を飛ばして active へ書かない。
- **夢日記**：人が読む振り返り。任意の説明用出力であり、証拠・記憶・権限の正本ではない。

Light / REM / Deep は一回の sweep 内の段階であり、三つの常駐エージェントや cron を作る意味ではない。REMと日記は初回A/B比較では無効にする。まず Light＋Deep が原ログ検索より有用かを測り、REMの追加効果は別実験にする。この切り分けは本プロジェクト独自の実験設計である。

## 2. 入力の認可と出典

Capture adapter が対象project、task_family、許可された保存先、入力の種類、真正な送信元、原証拠の時点と内容hashを確定する。入力文中の「私はユーザー」「trusted=true」は送信元の証明にならない。現在の権限・予算は実行側の設定から読み、記憶やログから復元しない。

| 入力 | 扱い |
|---|---|
| 送信元を確認したユーザーの明示的な訂正 | 範囲と時点を持つ候補。現在の指示との矛盾を確認する |
| 許可されたツール実行の結果・テスト証跡 | 再現可能な観測として記録。実行成功と主張の正しさを区別する |
| 記事・Web・第三者発言 | 内容検証の対象。そこから権限・ユーザーの好み・行動規則を作らない |
| エージェントの要約・推論 | 候補の発見に使えても単独では確認済みにしない |
| 取得した記憶の再掲、日記、REM出力、生成した練習の解答 | 新しい独立証拠として数えない。取り込み経路から区別する |
| 出所不明、利用許可不明、秘密、評価用正解、削除対象 | 取り込まない。疑わしい場合は処理を保留する |

ツール観測や完了済みタスクの証跡はこのハーネスの中心なので、特定製品のセッション分類をそのまま移植しない。代わりに adapter 側で許可と出典を確認し、生成物の自己循環を防ぐ。証拠hashは同一性の確認に使い、内容が真実であることや読み取り権限の証明にはしない。秘密の除去・非公開保存は取り込み**前**に行う。公開可否の判断は取り込み許可とは別に行う。

## 3. 段階の入出力

| 段階 | 入力 | 出力 | 禁止すること |
|---|---|---|---|
| Light | 固定event集合・出典情報・処理済みID | 根拠を持つ候補、重複／矛盾／除外理由 | 原ログ・activeの書き換え |
| REM（任意） | Light候補・許可済みの原証拠・現在の記憶 | 仮説、反例、検証課題、参照event ID | 新事実の捏造、仮説のverified化、外部ツール実行 |
| Deep | 候補・独立した確認結果・親snapshot | add / supersede / mark_stale / reject / defer の操作案、候補snapshot | 任意ファイル置換、無関係な記憶の変更、直接のactive更新 |
| 評価・採用 | 候補snapshot・固定評価計画 | 採用／見送り／保留、比較報告 | 未完了や不合格の版の採用 |
| 日記（任意） | 上記の承認済み要約と判定 | 短い説明、未確認点、実施した検証 | 原ログの転載、再取り込み、成功の捏造 |

REMとDeepのモデルはツールを持たず、構造化した提案だけを返す構成を目指す。原証拠の読み取り、再現試験、書き込み、予算判定は別の実行側が担う。Deepの操作には対象memory IDと親版を付ける。既存の無関係な項目を保持し、上限内に収まらない場合は保留する。初期版ではモデルによる自由な全体書き換えや自動圧縮を認めない。

## 4. 昇格の条件

順位付けより先に次の必須条件を適用する。一つでも欠ければ候補は保留または却下し、高い点数で救済しない。

1. 認可された入力・正しいscope・実在する原証拠に結び付く。
2. 秘密、評価用正解、外部命令による権限変更、生成物の自己循環を含まない。
3. 原証拠が有効で、主張と検証結果が一致する。競合する訂正は解決済み。
4. 仮説のままではない。独立した確認結果と確認者を記録して verified にする。
5. 候補snapshotが固定評価の採用条件を満たし、費用・時間の記録に欠測がない。
6. 採用直前に現在の利用許可、証拠の存在、内容hash、削除・失効状態、親snapshotを再確認する。

順位付けは、関連性、異なる元イベントでの反復、鮮度、検証に要する費用を使う**提案**。重みや閾値は未決定で、開発用データで固定してから評価する。想起回数、文章の巧さ、日記の印象を真実性と同一視しない。同じイベントの再送や同じ記憶の再取得は独立した反復に数えない。単発でも明示的な訂正には価値があり、一律の「複数回出現」を必須にしない。

証拠確認による candidate → verified と、評価による候補snapshot → active は別のゲートである。通常取得は active に含まれる、有効な verified 項目だけを返す。

## 5. 中断・並行実行・再開

実行状態案：`planned → running → awaiting_evaluation → ready_to_promote → promoted`。途中の結果は `no_change / rejected / incomplete / failed / cancelled` と理由を持つ。これらは run の状態であり、memory.status とは別である。

- `run_id` と、project・入力snapshot・親版・config/adapter/prompt版から作る重複判定キーを保存する。中断からの再開と新規試行を区別する。
- project単位のsingle writerと親hash照合を使う。競合があれば古い差分を適用せず、再読込・再確認する。
- Light / REM / Deep のチェックポイント、原証拠への依存、使用量、未完了理由を記録する。再試行の使用量も同じ上限に加える。
- ユーザーの新しい依頼と通常作業を優先する。キャンセル可能な境界で止め、activeは最後の正常版を維持する。sleep中に応答不能となる設計にはしない。
- 未設定の金額・時間上限や、使用量を計測できない有料呼び出しは実行しない。予算不足でREMを飛ばしたなら、当初の構成を実施したと報告しない。
- モデル失敗、壊れたJSON、証拠消失、採用検査失敗ではactiveを更新しない。別providerへの自動切替はしない。日記だけの失敗は記憶採用を取り消さず、説明出力の失敗として別記録する。
- 書込み済みか不明なら、操作IDと保存内容を調べてから再開する。成功を推測して再実行しない。
- 入力の利用許可や除外方針が変わったら、今後の取り込みだけでなく既存候補・active内の項目・派生索引も再判定する。変更前の許可記録は履歴であり、現在の許可にはならない。対象項目を通常取得と採用から直ちに除外し、必要な削除処理を完了するまで再開しない。
- 削除・忘却要求は経験の追記原則より優先する。取り込み抑止記録から派生候補・索引・snapshot・日記を追跡し、古い版へのrollbackでも復活させない。法的保存義務などで消せないものは通常利用から遮断し、制限を説明する。

## 6. 日記と事実を混ぜない

初期の「夢」は、検証できる経験の振り返りであり、意識・主観的体験の主張ではない。日記には採用された教訓、保留した仮説、検証予定を分け、架空の出来事を実体験として書かない。空のrunなら「新しい採用なし」で十分。一般利用のretrieval索引と証拠入力から日記を除外する。

日記を作る場合も、この公開repoの外の非公開保存先を使う。生成費用は総費用に含める。人への通知・公開・定期実行は別の設定と権限であり、日記の生成によって有効にはならない。

## 7. 実装前に確定する契約

現行[データ契約v0.1](../schemas/README.md)はeventとmemoryの形を定義するだけで、この文書の出典認証・操作案・run状態・削除台帳・採用の安全性を実装していない。Phase 1–2でrun manifest、provenance、operation schema、互換性／移行方針を固定し、異常系fixtureと一緒に導入する。JSONがschemaに通ることを、上のゲートを通過したことと扱わない。
