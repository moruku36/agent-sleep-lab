# 評価計画

状態：未実施。ここでの件数・予算・採用基準は初期の提案値。実験開始前に設定とデータ版を固定し、結果を見てから基準を動かさない。

## 問い

sleepを追加すると、記憶を持たない場合や原ログ検索だけの場合より、作業の成功と再現性が改善するか。回答時だけでなく整理・保守の費用を含めても価値があるか。

## 段階的な比較

| 条件 | 利用できる過去情報 | 目的 |
|---|---|---|
| A: raw retrieval | 同じ公開済み／利用許可済み原ログの検索 | 最初の比較対象 |
| B: consolidated memory | A＋整理・根拠確認した記憶 | 初回の主比較 |
| C: notes only | 整理前のノート＋原ログ検索 | 整理工程の寄与を調べる追加比較 |
| D: rehearsal | B＋過去経験から作った練習で確認した記憶 | Bの有用性確認後に追加 |
| Z: stateless | 過去情報なし | 必要な場合の参考比較 |

最初はA/Bだけを実施する。条件を増やすたびに別の実験として予算と仮説を記録する。モデル、バージョン、温度、ツール、タスク実行予算、現在のタスク指示を揃える。Aにも検索の指示と適切な予算を与え、弱い比較対象を作らない。

## データ分割

- **経験用**：既に完了したタスク、観測結果、訂正。sleepに渡せる。
- **開発用**：プロンプト・検索・採用基準の調整に使う。最終成績には混ぜない。
- **評価用**：sleepと調整に渡さない新しい課題・正解・採点基準。

同じ記事の別URL、翻訳、同じバグの派生課題は一群として分割する。タスク本文だけでなく正解や後日の訂正が経験側へ漏れていないか確認する。評価中は記憶snapshotを固定し、条件間で出力や正解を共有しない。評価が終わるまで結果を次のsleepへ取り込まない。

## 初回パイロット

合成または公開可能な論文整理課題を用いる。まず5件の接続確認を行うが、これは性能の結論に使わない。手順が通った後、別の20件をA/Bそれぞれ新規セッションで解く。予算が許せば各3回。実行順は対応する課題ごとに入れ替え、失敗・タイムアウトを除外しない。

20件は小規模な探索評価であり、有意な差を保証しない。同じ課題の反復を独立した60件と数えず、課題単位で集計する。

## 指標と採点

| 指標 | 定義 |
|---|---|
| 主指標：タスク成功率 | 事前に固定した必須要件をすべて満たした課題数／全課題数 |
| 要件充足率 | 正確な引用、分類、形式、結果と提案の区別など、基準ごとの充足数 |
| 訂正回数 | 人が修正を要求した回数。無介入の比較では未測定と明記 |
| 同じ失敗の再発 | 事前定義した誤り分類ごとの再発件数／該当する機会数 |
| 記憶の品質 | 根拠なし・古い事実・適用範囲違いの利用件数、根拠に戻れる割合 |
| 運用負担 | 取得時間、整理時間、回答時間、メモリーサイズ、トークン、実費 |

形式・リンク・必須項目は可能な範囲で決定的に採点する。意味の評価は条件を隠して人が確認する。LLM評価器を使う場合も、人による一部照合と不一致の記録を行い、実行したモデル自身の自己評価だけで成功と判定しない。

## 費用

`total_cost = capture + consolidation + verification + retrieval + task_execution + maintenance + evaluation`

実験の実費は評価費用も含めて報告する。日常運用の見積もりは評価費用を別表示し、整理費用を次の20件／100件へ償却した場合も併記する。回答時に節約したトークンだけを総費用削減と呼ばない。

支払いを伴う実行前にモデル・単価・通貨・上限額を確定する。初期設定の金額上限はnullで、実行を許可しない。人が金額を埋めるか、既存の明示された予算を設定に取り込む。データ収集や整理に上限を超える再試行をしない。

## 採用と結論

個々の記憶をverifiedへ進める根拠確認と、snapshotを運用採用する性能評価は別とする。

初回の試験採用は、Aに対してタスク成功数が悪化せず、根拠なしの事実や外部命令の採用が増えず、整理費償却後の1件当たり費用が事前に決めた上限（初期案はAの1.3倍）以内の場合に限る。時間の上限も実験前に定める。欠測や未完了がある場合は採用を保留する。

「性能向上を確認」と述べるには、独立した評価セットで主指標が改善し、課題単位の対応付き差と95%区間を示す。差が不確かな場合は「探索的に改善傾向」「差を確認できず」と記録する。小規模パイロットだけで一般性能の向上を主張しない。

採用しなかった場合も、結果と理由を残す。次の改善案の調整には開発用データを使い、評価セットを繰り返し最適化しない。
